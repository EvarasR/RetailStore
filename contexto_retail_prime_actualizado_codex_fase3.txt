============================================================
1. RESUMEN GENERAL DEL PROYECTO
============================================================

Nombre principal del proyecto:
Sistema de tienda retail con gestión de miembros premium y beneficios tipo Prime.

Nombre técnico sugerido:
Retail Prime - Plataforma e-commerce retail para productos de informática y redes.

Objetivo:
Construir una aplicación web tipo Amazon, pero adaptada a un proyecto académico/técnico, usando Python, Django y PostgreSQL 15. El sistema debe vender al consumidor final, gestionar productos, proveedores, inventario, carrito, checkout, pagos simulados, tracking de pedidos, membresías premium tipo Prime, beneficios, notificaciones, reportes y reglas de negocio automatizadas.

El nicho final elegido ya NO es generalista. Se cambió a:
Productos de informática, redes, seguridad de red, cableado estructurado, servidores, periféricos, almacenamiento, videovigilancia IP, UPS, racks, herramientas de red y equipos empresariales.

3. DECISIÓN ARQUITECTÓNICA MÁS IMPORTANTE
============================================================

El proyecto seguirá un enfoque DB-first.

La lógica principal del sistema vivirá en PostgreSQL 15 mediante:
- Funciones SQL/PLpgSQL.
- Triggers.
- Constraints.
- Foreign keys.
- Índices.
- Validaciones de integridad.
- Automatización de estados.
- Auditoría.

Django NO debe ser quien haga toda la lógica crítica de negocio de manera dispersa. Django debe:
- Mostrar templates.
- Recibir formularios.
- Validar datos de entrada a nivel de interfaz.
- Manejar sesiones y autenticación.
- Llamar funciones SQL.
- Consumir respuestas JSON.
- Renderizar paneles.
- Integrarse posteriormente con React si se decide migrar el frontend.

La base de datos debe ser el núcleo fuerte del sistema.

Frase guía:
Si la base de datos queda bien, Django fluye. Si la base queda mal, Django solo maquilla el desastre.

============================================================
5. NORMALIZACIÓN Y CONVENCIÓN DE IDs
============================================================

La base de datos debe estar normalizada, preferentemente en 3FN.

Criterios:
- 1FN: campos atómicos, sin listas dentro de una columna.
- 2FN: atributos dependientes de toda la clave.
- 3FN: no depender de atributos no clave.

Convención de IDs:
Usar claves primarias con nombres tipo:
- cod_usuario
- cod_producto
- cod_proveedor
- cod_pedido
- cod_pago
- cod_envio
- cod_membresia
- cod_categoria
- cod_marca

Se recomienda snake_case, no nombres pegados.

Ejemplo correcto:
cod_usuario

Ejemplo no recomendado:
codusuario

Las tablas deben tener constraints, foreign keys, índices únicos y checks.

9. REGLAS DE NEGOCIO DEFINIDAS
============================================================

9.1 Regla retail
La tienda vende al consumidor final, no al mayorista.

Por eso debe haber límites de compra por producto o categoría.

Ejemplos:
- Firewalls: máximo 2 por pedido.
- Routers: máximo 3 por pedido.
- Switches: máximo 5 por pedido.
- Access Points: máximo 10 por pedido.
- Cables: límite mayor, porque es normal comprar varias unidades.
- Herramientas: límite moderado.

Si un cliente pide una cantidad exagerada, el sistema debe:
- Rechazar la compra.
- O marcarla como requiere revisión.
- O sugerir contactar a soporte.

9.2 Regla de producto publicable
Un producto puede crearse en estado BORRADOR, pero solo puede pasar a PUBLICADO si cumple:
- Tiene categoría.
- Tiene marca.
- Tiene SKU único.
- Tiene precio mayor a cero.
- Tiene imagen principal.
- Tiene límite retail configurado.
- Tiene mínimo 5 proveedores activos.
- Tiene stock propio o stock disponible en proveedores.

9.3 Regla de mínimo 5 proveedores
Cada producto debe tener mínimo 5 proveedores activos para poder estar publicado.

Un proveedor puede proveer varios productos.
Un producto puede estar asociado a varios proveedores.

Relación clave:
producto 1 --- N producto_proveedor N --- 1 proveedor

9.4 Regla de stock propio + proveedores
Si el cliente pide una cantidad y el stock propio no alcanza:

Ejemplo:
Cantidad solicitada: 10
Stock propio: 4
Faltante: 6

El sistema debe:
1. Reservar stock propio disponible.
2. Buscar proveedores activos del producto.
3. Ordenarlos por prioridad, costo y tiempo de entrega.
4. Cubrir el faltante con uno o más proveedores.
5. Generar orden de abastecimiento si corresponde.
6. Marcar el pedido como WAITING_SUPPLIER o estado equivalente.

Si no se puede cubrir el faltante:
- Rechazar compra.
- O permitir solo la cantidad disponible.

9.5 Regla de pago simulado
La pasarela de pago será simulada, pero debe comportarse como una real.

Debe validar:
- Marca de tarjeta.
- BIN.
- Algoritmo Luhn.
- Fecha de expiración.
- CVV.
- Saldo disponible.
- Límite diario.
- Estado de tarjeta.
- Tarjeta bloqueada.
- Monto del pedido.
- Idempotencia.

No guardar CVV.
No guardar número completo de tarjeta.
Guardar solamente:
- Marca.
- BIN parcial.
- Últimos 4 dígitos.
- Token simulado.
- Nombre del titular.
- Fecha de vencimiento.

Estados de pago:
- INICIADO
- VALIDANDO
- AUTORIZADO
- RECHAZADO
- CAPTURADO
- FALLIDO
- REEMBOLSADO
- ANULADO

9.6 Regla de tracking automático
Cada cambio importante del pedido debe generar evento de tracking.

Eventos posibles:
- Pedido creado.
- Pago aprobado.
- Preparando pedido.
- Esperando proveedor.
- Listo para enviar.
- Recogido por transportista.
- En tránsito.
- Llegó a centro local.
- En reparto.
- Entregado.
- Devolución solicitada.
- Devuelto.

9.7 Regla de membresía premium
El cliente premium tendrá beneficios tipo Prime:
- Envío gratis.
- Entrega prioritaria.
- Descuentos exclusivos.
- Acceso anticipado.
- Compras recurrentes.
- Mayor plazo de devolución.
- Promociones tipo “Suscríbete y ahorra”.

Pero premium NO debe saltarse reglas críticas:
- No elimina límites retail.
- No permite comprar sin stock.
- No evita validación de pago.
- No permite saltar controles antifraude.

13. ERRORES YA DETECTADOS Y CORREGIDOS
============================================================

1. Problema con schema retail:
Inicialmente algunos archivos usaban schema retail o SET search_path = retail, public.
Decisión final: quitar eso. Todo va en public.

2. Drops al inicio:
El usuario pidió que estructura.sql tenga DROP TABLE IF EXISTS ... CASCADE al inicio.
Eso debe mantenerse.

3. Error en datos.sql con fn_registrar_metodo_pago_simulado:
Error:
ERROR: no existe la función fn_registrar_metodo_pago_simulado(bigint, unknown, unknown, integer, integer, unknown, integer, integer)

Causa:
La función estaba definida con tipos más específicos, por ejemplo SMALLINT o NUMERIC, y datos.sql llamaba con INTEGER/unknown.

Solución aplicada:
- Agregar firma compatible en funciones.sql.
- O castear explícitamente en datos.sql.

4. Cambio de nicho:
El usuario pidió cambiar los datos de productos a informática y redes.
Se modificó datos.sql para ese nicho.

14. CÓMO DEBE CONECTARSE DJANGO CON LA BASE
============================================================

Django debe usar modelos para representar tablas, pero la lógica crítica debe llamar funciones SQL.

Ejemplo conceptual desde Django:

with connection.cursor() as cursor:
    cursor.execute(
        "SELECT fn_agregar_producto_carrito(%s, %s, %s)",
        [cod_usuario, cod_producto, cantidad]
    )
    resultado = cursor.fetchone()

Django debe tener servicios/repositorios para encapsular llamadas SQL, por ejemplo:

apps/clientes/services/carrito_service.py
apps/operaciones/services/pago_service.py
apps/proveedores/services/abastecimiento_service.py
apps/administracion/services/producto_service.py

No poner llamadas SQL desordenadas dentro de todas las vistas.

Estructura sugerida:

apps/
  core/
    models.py
    services/
    views.py
    urls.py
  clientes/
    models.py

36. ACTUALIZACIÓN FASE 1.1 - LOGIN Y HASH DE CONTRASEÑAS EN POSTGRESQL
============================================================

Fecha de actualización: 2026-06-12

Problema detectado:
Al intentar iniciar sesión en /login/, Django lanzó:
ValueError: not enough values to unpack (expected 4, got 2).

Causa:
En datos.sql los usuarios de prueba tenían password_hash = 'pbkdf2_sha256$demo'.
Ese texto no es un hash Django válido. Django espera el formato:
pbkdf2_sha256$iteraciones$salt$hash.

Decisión aplicada:
El hash de las contraseñas demo debe generarse en PostgreSQL, no manualmente desde Python ni con valores simulados.

Cambios aplicados:
1. funciones.sql
- Se agregó fn_generar_password_hash_django(p_password, p_salt, p_iterations).
- La función implementa PBKDF2-HMAC-SHA256 usando pgcrypto.
- Devuelve un hash compatible con Django AbstractBaseUser/check_password.
- Se agregó fn_cambiar_password_usuario(p_cod_usuario, p_password, p_iterations) para cambiar contraseñas desde PostgreSQL usando texto plano de entrada y guardando solo el hash.
- Se endureció fn_cambiar_password_simulado para rechazar hashes que no cumplan el patrón pbkdf2_sha256$iteraciones$salt$hash.

2. datos.sql
- Se reemplazó 'pbkdf2_sha256$demo' por llamadas a fn_generar_password_hash_django().
- La contraseña demo para todos los usuarios sembrados es: RetailPrime2026*
- ON CONFLICT (email) ahora actualiza también password_hash para corregir usuarios existentes si se reejecuta datos.sql.

3. sql_fix_passwords_demo.sql
- Se creó un script independiente para actualizar la base actual sin recrear toda la BD.
- Crea/actualiza las funciones necesarias y actualiza password_hash de los usuarios demo.
- Debe ejecutarse una vez sobre la base actual si ya se cargó el datos.sql antiguo.

4. apps/core/views.py
- login_view ahora captura ValueError durante authenticate().
- Si existe un hash malformado, el login no tumba el servidor con traceback.
- En DEBUG=True muestra mensaje técnico indicando ejecutar sql_fix_passwords_demo.sql.
- En producción muestra un mensaje genérico.

Credenciales demo después del fix:
- admin@retailprime.local / RetailPrime2026*
- ana.cliente@example.com / RetailPrime2026*
- carla.prime@example.com / RetailPrime2026*

2. Relaciones administrables:
   Deben tener asociar, actualizar, desasociar y listar.

3. Tablas transaccionales:
   Deben usar funciones de negocio y cambios de estado; no DELETE genérico.
