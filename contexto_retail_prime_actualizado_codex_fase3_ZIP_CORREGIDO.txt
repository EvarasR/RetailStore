============================================================
1. RESUMEN EJECUTIVO
============================================================

Proyecto:
Retail Prime.

Tipo de sistema:
Tienda web retail tipo Amazon simplificada, enfocada en consumidor final, con membresías tipo Prime, catálogo, carrito, checkout, pago simulado, tracking, proveedores, reposición, inventario, promociones, reseñas, wishlist, soporte, reportes y panel administrativo.

Nicho definitivo:
Informática, redes, seguridad de red, cableado estructurado, servidores, almacenamiento, videovigilancia IP, UPS, racks, herramientas de red, laptops empresariales y periféricos.

Stack:
- Django 5.2.x.
- PostgreSQL 15.
- psycopg 3.
- Django Templates.
- APIs internas JSON consumidas con fetch/JS.
- CSS propio, sin Bootstrap.

Arquitectura:
Monolito modular Django + PostgreSQL DB-first.

Principio central:
La lógica crítica vive en PostgreSQL mediante funciones, triggers, constraints, foreign keys, índices, validaciones, auditoría y automatización. Django autentica, valida entradas, renderiza, expone APIs internas y llama funciones SQL desde services.

============================================================
6. DECISIONES ARQUITECTÓNICAS VIGENTES
============================================================

1. DB-first.
2. Esquema public, no schema retail.
3. IDs en snake_case tipo cod_usuario, cod_producto, cod_proveedor.
4. Tablas principales controladas por SQL; modelos Django con managed=False.
5. Django llama funciones SQL desde services.
6. Las views no deben tener lógica crítica de negocio.
7. Templates consumen APIs internas JSON.
8. React queda para después.
9. Docker queda para el final.
10. CSS propio, sin Bootstrap.
11. Admin nativo de Django solo soporte/desarrollo, no interfaz principal.

============================================================
7. REGLAS DE NEGOCIO VIGENTES
============================================================

Retail:
La tienda vende al consumidor final. No vende al mayorista. Deben existir límites de compra por producto/categoría.

Producto publicable:
Un producto solo se publica si tiene categoría, marca, SKU único, precio de exhibición mayor a cero, imagen principal, límite retail, mínimo 5 proveedores activos y stock propio o stock de proveedor.

Proveedores:
Un producto debe tener mínimo 5 proveedores activos para poder estar publicado. Un proveedor puede proveer muchos productos.

Inventario:
La tienda intenta no dejar de vender mediante stock propio + proveedores + reposición preventiva. Esto no significa stock infinito; si proveedores no cubren, se debe alertar y bloquear/limitar.

Lotes:
Debe existir trazabilidad por lote/tandada: costo histórico, PVP calculado, stock disponible/reservado y asignación FIFO al pedido.

Precio:
producto.precio_actual debe ser precio de exhibición o “desde”. El cobro real debe salir de lotes + función única de precio final.

Prime:
Prime da beneficios, pero no salta límites retail, stock, pago, antifraude ni validaciones.

Pago simulado:
Debe validar tarjeta, BIN, Luhn, expiración, CVV, saldo, límites, estado, idempotencia. No guardar CVV ni PAN completo.

Tracking:
Debe ser persistente en base de datos y progresivo; no depender únicamente de una simulación en Django.

Auditoría:
Tablas históricas, pagos, factura, tracking, movimientos, reservas históricas y auditoría no deben tener DELETE físico genérico.
